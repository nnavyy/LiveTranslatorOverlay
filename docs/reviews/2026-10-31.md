# Live Translator Overlay — app review and improvement report

Reviewed: **31 October 2026, Asia/Jakarta**\
Version: **1.3.3**\
Source: `e1362bec63f05bfaca34d1c67deec3470a0bb81e`\
Scope: reliability, translation correctness, updates and user notifications, feedback tracking, privacy, interface usability, and language expansion. **Spoken/translated languages and interface languages have equal priority**, following your preference.

## Main recommendation

Stabilize translation correctness and the updater before expanding the language list. The app builds successfully and already has useful foundations: interchangeable translation providers, local Windows OCR, two speech engines, searchable language selectors, translation history, localization, and an update-ready banner.

The biggest problems affect trust: changed numbers can receive an old translation; ordinary replies are deliberately filtered; reports can be labeled fixed without a corresponding fix; and updates can restart the app while the user is interacting with settings. Improve these first, then add a persistent “What’s new” experience and expand both language categories together.

**This is a review, not a patch release. No application fixes were applied.** The added review probes document current defects.

### F01 — A changed number can retain the old translation

**Location:** [GroqTranslateProvider.cs:378](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/Translation/GroqTranslateProvider.cs#L378) and its streaming equivalent at line 506.

The provider returns cached output when the new input is more than 88% similar to the previous input. The probe seeded a prior translation of “The price is 100 dollars.” and requested “The price is 900 dollars.” Both normal and streaming methods returned **“Harganya 100 dolar.”** This is an application cache decision, independent of model quality.

**Fix:** Reuse completed translations only for an exact request match, including language, script style, provider/model, and relevant context. Keep OCR noise suppression separate from translation correctness. **Acceptance:** Changes to numbers, names, dates, and negation produce a new request; an identical request can use cache.

### F02 — The hallucination filter removes real dialogue

**Location:** [HallucinationDetector.cs:117](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/HallucinationDetector.cs#L117), especially line 164; audio callers also apply this filter to translated output.

The probe confirmed rejection of all eight valid examples: **yes, no, thank you, terima kasih, спасибо, 你好, はい, 안녕**. A blanket two-character cutoff particularly harms languages where a short written phrase is complete. Filtering translated output can hide a valid longer source utterance whose translation is short.

**Fix:** Use silence/voice evidence, recognition confidence, and repetition together; ordinary words alone should not prove hallucination. Give translation output a separate validation path. **Acceptance:** These phrases survive voiced/high-confidence cases while silence, isolated clicks, and known repetitive model artifacts remain suppressed. Test with native speakers.

### F03 — Short audio is held indefinitely

**Location:** [AudioCaptureService.cs:31](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/AudioCaptureService.cs#L31) and line 256.

The stagnant-playback flush only runs after the four-second minimum is reached. Two seconds of synthetic voiced samples followed by 1.3 seconds without new samples produced zero chunks; adding another two seconds allowed emission. A short game line or notification can therefore wait for unrelated later audio, and Stop does not flush the remaining chunk.

**Fix:** Allow a voiced short segment to flush after a bounded silence/no-data interval. Define explicitly whether Stop discards or completes pending speech. Keep enough context for recognition and avoid sending silence. **Acceptance:** A one- or two-second phrase followed by paused playback is emitted within the configured silence deadline. Measure the accuracy/latency tradeoff using actual speech.

### F04 — “Fixed” does not mean the issue was fixed

**Location:** [FeedbackHistoryManager.cs:151](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/Feedback/FeedbackHistoryManager.cs#L151) and line 170.

Pending reports automatically become Fixed when either the latest release or the installed version is newer than the report version. There is no requirement that the release addresses that report. The generic version pass can also override an explicit remote Pending status. This applies to feature requests and general feedback as well as bugs.

**Fix:** Resolve a report only through an explicit report/issue mapping with `fixedInVersion` and a resolution note. Distinguish **“Fix available in vX”** from **“Fix installed in vX.”** Keep unrelated reports open. **Acceptance:** An unrelated release never resolves a report; remote status is respected; users see the linked fix and can report that it still happens.

### F05 — Update installation can disrupt other work and leave partial files

**Location:** [AutoUpdaterService.cs:148](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/Update/AutoUpdaterService.cs#L148), helper script at line 259, copy result at line 274.

The downloader and helper terminate robocopy processes by name, including copies unrelated to this app. The helper records the robocopy exit code but unconditionally deletes staging and relaunches afterward. It does not branch on a failed copy or restore a previous version. The first ZIP asset is selected without matching platform/architecture or checking required executable files. No explicit package digest/signature validation is present.

**Fix:** Remove global process termination. Manage only the current app/update helper; wait for graceful app exit. Select the expected asset, validate its contents and integrity, preserve the prior installation, treat robocopy failure codes correctly, and retain recovery files on failure. Persist the result so startup can report success or failure. **Acceptance:** Locked files, insufficient space, corrupt ZIP, wrong asset, and unwritable installation folder preserve a launchable version; unrelated file copies continue. These installation tests remain to be run in a disposable environment.

### F06 — Update timing does not reflect user activity

**Location:** [MainWindow.xaml.cs:1135](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/MainWindow.xaml.cs#L1135); `_lastUserActivity` is initialized at startup and updated only in the OCR loop at line 1404. Close paths also call ApplyUpdateAndRestart.

After 15 seconds, “idle” can include editing settings, composing feedback, or reading history. The app may restart without an explicit restart action. Applying an update while closing also relaunches the app when the user intended to quit.

**Fix:** Default to **Restart now / Later**. If automatic installation is offered, make it a preference and account for real input and unsaved work. Separate **install-and-exit** from **install-and-restart**. **Acceptance:** Typing feedback or changing settings cannot trigger a restart; quitting stays quit; active speech/OCR continues until a deliberate safe stop.

### F07 — Production debug logs retain conversation content

**Location:** [DiarizedSttService.cs:135](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/DiarizedSttService.cs#L135) and [WhisperSttService.cs:226](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/WhisperSttService.cs#L226).

Deepgram responses and Groq transcripts are appended to local debug files during normal operation. The normal history buffer may be temporary, but these additional files persist. This retention is not clearly explained in the user-facing privacy documentation. The Google provider also sends text to MyMemory as fallback, while the policy’s cloud-services list omits that recipient.

**Fix:** Disable content logging by default. Make diagnostics opt-in, redact content/secrets, rotate and expire logs, expose a delete action, and describe every actual recipient. Avoid an “anonymous” label when feedback includes Windows username and machine name; let users preview and remove optional identifying diagnostics. **Acceptance:** Normal use produces no raw transcript logs; diagnostic exports contain no API keys or unnecessary conversation text; the privacy description matches the network paths.

### F08 — Queue limits and cancellation do not cover the async work

**Location:** [AudioCaptureService.cs:314](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/Core/AudioCaptureService.cs#L314), [MainWindow.xaml.cs:1639](https://github.com/nnavyy/LiveTranslatorOverlay/blob/e1362bec63f05bfaca34d1c67deec3470a0bb81e/MainWindow.xaml.cs#L1639), and line 1771.

The two-slot semaphore is released after invoking an EventHandler. An async event handler returns at its first await, so the semaphore does not wait for processing. The probe observed **four concurrent consumers** despite the intended limit of two. Whisper itself has a nonblocking transcription lock, but the surrounding pipeline can still drop chunks or overlap later translations.

Deepgram raw-audio events can similarly overlap SendAsync calls. Microsoft documents that concurrent WebSocket sends must be serialized. Stop cancels a mutable field, while existing HTTP/translation operations do not receive a session token; a rapid stop/start can let old work affect a new session. Unexpected recording termination does not set `_isCapturing` false or notify the UI, and a closed Deepgram stream has no visible reconnection path. [Microsoft WebSocket documentation](https://learn.microsoft.com/en-us/dotnet/api/system.net.websockets.clientwebsocket.sendasync?view=net-10.0).

**Fix:** Use one bounded, awaited consumer per audio pipeline and one serialized WebSocket sender. Capture immutable session IDs/tokens, propagate cancellation into requests/stream reads, and discard obsolete results. Expose Disconnected/Reconnecting states and reset UI/resources after capture failure. Add a read-stall deadline: response-header timeouts alone do not bound the current streaming read loops. **Acceptance:** Queue capacity is enforced under a slow consumer; no simultaneous sends; stopped sessions cannot update captions; unplugging a device/network disconnect gives a recoverable state. Only the queue defect was reproduced offline; those additional scenarios need integration tests.

## Update notifications and “What’s new”

The app already checks GitHub, downloads updates, and exposes a restart banner. It does **not** currently parse release descriptions into a user-facing changelog, remember which release notes the user has seen, or present a persistent installed-update history. The release workflow’s generated GitHub notes do not replace an in-app explanation.

### Desired user experience

| Event | User message/action | Behavior |
|---|---|---|
| New release available | “A new version is available — see what changed.” | One nonblocking notice per version with View changes; do not repeat every 15-minute poll. |
| Downloading | Progress in the Updates area | Quiet by default; do not cover live captions. |
| Ready to install | “Update ready. Restart when convenient.” | Restart now / Later; preserve work before installation. |
| First launch after successful installation | “Updated to vX — here’s what changed.” | Show once, with Added / Improved / Fixed / Known issues. Keep it available later. |
| A submitted issue has a released fix | “A fix for your report is available in vX.” | Link the report and release entry. Say whether the fix is installed. |
| Update fails | “Update couldn’t be installed. Your previous version is available.” | Only promise recovery after verifying it. Offer Retry and diagnostic details. |
| Nothing changed | No routine toast | Update the status/date in Settings; remain quiet during normal checks. |

For every installed release, show **one notice containing all relevant improvements and fixes**. Avoid a separate popup for every bullet. Provide a Settings → Updates page with current version, last successful check, pending version, release history, and notification preferences. If several versions were skipped, group all unseen changes since the last acknowledged version.

### Minimum release data

Reuse GitHub releases and the existing report-status feed initially; a new backend is not required just for release notes. Add a small structured manifest if needed for reliable categorization and localization.

| Field | Purpose |
|---|---|
| version, publication date, release URL | Identify the release consistently. |
| added, improved, fixed, knownIssues | Clear user-facing categories, each with stable entry IDs. |
| localized text plus English fallback | Release notes follow interface language without blocking installation if a translation is missing. |
| issue/report mapping, fixedInVersion | Link a verified resolution to a specific release. Keep personal report contents out of public manifests. |
| asset name, platform/architecture, integrity metadata | Select and validate the correct update package. |
| installedVersion, previousVersion, lastSeenReleaseVersion, installOutcome | Remember what was installed and which notices have already been shown. |

Treat remote release content as untrusted text: validate shape and size, restrict links to safe web schemes, and never execute embedded markup/scripts. Cache the last good changelog for offline viewing. Persist install success only after the new executable starts and reports the expected version. Keep a single version source and verify release tag/package version agreement in CI.

**Example copy for a future release, only after the listed fixes are implemented and verified:**

> Updated to vX.Y.Z\
> Fixed: changed numbers now receive a fresh translation.\
> Fixed: short spoken replies no longer disappear.\
> Improved: updates wait until you choose to restart.\
> Added: see this release’s supported new languages here.\
> View all changes · View my reports · Got it

**Notification acceptance checks:** Once-per-version display survives restart; failed install never shows “updated”; skipped releases remain discoverable; offline startup displays cached notes; changing interface language changes the notes; quiet preferences suppress optional toasts; report updates never claim an unrelated bug was fixed. Users must be able to reopen dismissed notes.

## Language expansion — equal attention to speech/output and menus

### Keep four capabilities separate

1. **Speech input:** supported by the selected speech model and its language configuration.
2. **Translated output:** supported by the translation provider and script conversion behavior.
3. **Screen OCR input:** supported by installed Windows OCR language packs.
4. **Interface:** menus, errors, help, feedback, update notifications, and release notes actually localized.

A language appearing in the translation list does not prove support for the other three. Surface badges such as “Speech supported,” “OCR pack required,” and “Menus unavailable in this language.” Windows exposes the OCR languages available on the device; use that list rather than assuming a language pack is installed. [Microsoft OCR language availability](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine.availablerecognizerlanguages?view=winrt-28000).

### Proposed expansion order

This is an initial product proposal based on the app’s Indonesian/English context and its existing East Asian and international language options, not measured user-demand data. Give each language release both speech/output work and interface-localization work; native review availability should influence the exact order.

| Milestone | New speech/translation selector candidates | New interface languages | Release condition |
|---|---|---|---|
| First language release | Malay (`ms`), Vietnamese (`vi`), Thai (`th`), Filipino/Tagalog (canonical UI tag with provider-specific `tl` mapping as needed) | Spanish, Japanese, Korean, Simplified Chinese; these already exist as translation choices | Capability mappings, errors, onboarding, and update notes verified for each shipped locale. |
| Second language release | Portuguese, Hindi, Turkish, Italian, Dutch, Polish | Malay, Vietnamese, Thai, Filipino/Tagalog | Native review and provider/OCR checks completed; no loss of current language preferences. |
| Following release | Additional languages selected from requests and measured quality | Portuguese and Arabic, then other requested locales | Arabic requires full bidirectional-layout, mixed-number/punctuation, font, keyboard, and screen-reader checks. Arabic text translation already appears in the app today. |

These are candidate sets, not a requirement to ship all listed languages at once. Ship smaller reviewed groups if translation resources are limited, while keeping both tracks funded equally.

The current Deepgram matrix lists Malay, Vietnamese, and Thai for Nova-2; Filipino/Tagalog needs a compatible model, such as the listed Nova-3 `tl` configuration, rather than assuming support in the app’s current Nova-2 path. Validate each exact provider code, streaming mode, and chosen model before enabling it. Groq documents multilingual Whisper models, but that does not establish equal accuracy across accents or languages. [Deepgram model/language matrix](https://developers.deepgram.com/docs/models-languages-overview/), [Groq speech-to-text documentation](https://console.groq.com/docs/speech-to-text).

### Implementation needed before adding selector entries

- Store a single small language catalog with stable tags, English/native display names, direction, script variants, and provider-specific mappings. Generate selectors from it instead of editing XAML, localized labels, target detection, prompts, and service mappings independently.
- Preserve the existing tag-based source/target preferences. Migrate UI language selection away from list indices so adding/reordering interface languages cannot change a saved selection.
- Move interface strings into per-locale resources, with English fallback and checks for missing keys, invalid format placeholders, and untranslated errors/tooltips. Existing hardcoded English/Indonesian runtime status messages need inclusion.
- Use regional tags where meaningful, including Chinese scripts and Portuguese variants. Keep script/transliteration preferences separate from the language identity.
- Enable only valid model/language pairs. If a chosen OCR pack is absent, explain how to install it; if speech input is unsupported, offer an explicit compatible engine. Never silently change the selected source language.
- Test short replies, names, numbers, negation, code-switching, and no-space scripts in the hallucination filter. Test the original transcript and translation independently.

**Per-language acceptance:** Native review of menus and update notices; representative clean/noisy speech; source/output combinations; already-target-language text; pack-present/pack-missing OCR; font rendering and wrapping; settings persistence; correct fallback messaging. Record measured transcription error and caption latency by language/model before claiming quality or “real-time” performance.
